## 1. 観測対象・宇宙の状態

### Q. アンテナから取れるデータで宇宙の状態がわかるものにはどんなものがあるか？

**A.**
アンテナとRTL-SDRが受信する物理的な生データは、IT/ネットワーク的に言えば**「宇宙から届く生パケット（電波の受信時刻・周波数・強度）」**です。
これらをデジタル信号処理（[FFT](00_glossary.md#fft) や [積算](00_glossary.md#integration)）して解析することで、宇宙の様々な物理状態（メトリクス）を可視化できます。

主な観測対象と把握できる「宇宙の状態」は以下の通りです：

#### 1. 太陽フレア・宇宙天気（Solar Radio Burst）
- **受信データ**: 太陽方向を指向した際の広帯域ノイズフロアの急激な跳ね上がり、および高周波から低周波へと周波数が推移していく波形。
- **わかる宇宙の状態**:
  - 太陽表面の磁気リコネクションによる大規模爆発（太陽フレア）の発生。
  - プラズマ衝撃波（コロナ質量放出: CME）が宇宙空間へ吹き出す速度。
  - 地球の磁気圏・電離層嵐（デリンジャー現象）による通信障害やGPS誤差の予兆。

#### 2. 流星の大気圏突入・電離層状態（流星電波前方散乱観測）
- **受信データ**: 遠方の電波送信所（福井高専 53.57MHz など）の電波が、流星が通過した瞬間だけ強く反射して届くエコー信号（「ピキーン」というスパイク）。
- **わかる宇宙の状態**:
  - 宇宙のチリ（流星物質）が秒速数十kmで地球大気圏に突入した瞬間と頻度。
  - エコー持続時間や強度から推定されるチリの質量・規模。
  - 太陽活動や昼夜に伴う地球電離層（プラズマ層）の電子密度・異常伝搬状態。

#### 3. 天の川銀河の回転・星間ガス・ダークマター（[21cm線](00_glossary.md#21cm)）
- **受信データ**: 1420.405MHz 付近のスペクトルの山（ピーク）と、その周波数ズレ（[ドップラー効果](00_glossary.md#doppler)）。
- **わかる宇宙の状態**:
  - **銀河の腕の速度**: ガスの塊が地球に対して秒速何十kmで公転・移動しているか。
  - **星間物質の分布**: 光では見えない冷たい水素ガスの濃淡と構造。
  - **ダークマター（暗黒物質）の存在証明**: ニュートン力学から予測される回転速度と実測値の乖離（[銀河回転曲線](00_glossary.md#rotation-curve)のフラット化）。

#### 4. 木星と衛星イオの電磁気相互作用（木星電波バースト）
- **受信データ**: 20MHz前後の短波帯で受信される「波の音」のような特徴的なノイズ（Lバースト / Sバースト）。
- **わかる宇宙の状態**:
  - 木星の衛星イオの火山活動ガスが木星の強力な磁場と衝突し、数百万アンペア規模のオーロラ電流が発生している状態。
  - 木星と衛星イオの相対的な公転位置。

#### 5. 人工衛星テレメトリ＆地球環境画像（衛星ダウンリンク）
- **受信データ**: 137MHz帯（NOAA気象衛星のAPT電波）や 430MHz帯（超小型衛星 CubeSat）の信号。
- **わかる宇宙の状態**:
  - 宇宙空間（高度800km）から見た地球のリアルタイムな雲の分布、台風、海水温。
  - 人工衛星の姿勢、外壁温度（日照面+100℃ / 影-100℃）、バッテリー残量などのヘルス状態。

#### まとめ（メトリクス対応表）

| 宇宙の状態 (Metrics) | 物理現象 (Logs / Traces) | 観測周波数帯 | 自宅での難易度 |
| :--- | :--- | :--- | :--- |
| **流星の突入頻度・規模** | 反射エコー（ピーク検知・持続時間） | 50MHz帯 | ★☆☆（付属アンテナで即可能） |
| **地球の雲・台風・海** | 衛星からのダウンリンク画像 | 137MHz帯 | ★★☆（Vダイポール自作で可能） |
| **太陽フレア・宇宙天気** | 広帯域ノイズフロアの急上昇 | 数十〜数百MHz | ★★☆（広帯域アンテナで晴天時） |
| **銀河回転・星間ガス** | 1420MHzのドップラーシフトスペクトル | 1420MHz | ★★★（専用アンテナ+LNAが必要） |
| **木星と衛星の磁気嵐** | 20MHz帯のバースト音 | 20MHz帯 | ★★★（低ノイズ環境・長尺アンテナ） |

## 2. アンテナ選定・ハードウェア＆設置環境

### Q. 市販のアンテナでそのような面白い観測ができるものなのか？

**A.**
**十分に可能です。しかも「RTL-SDR付属の伸縮アンテナ」だけでも今すぐ観測できる対象があります。**

アンテナの調達コスト・自作難易度別にできる観測は以下の通りです：

#### 1. 付属の伸縮アンテナだけで「今日から即可能」な観測
- **流星電波観測（大気圏突入エコー検知）**:
  - 付属のロッドアンテナを両側約1.4m（53MHz帯の半波長ダイポール）に伸ばすだけで、福井高専等の送信所からの前方散乱エコーを捉えることができます。
- **気象衛星 NOAA / ISS（宇宙からの地球雲画像・テレメトリ）**:
  - 付属アンテナのエレメント長を約53cmに縮め、開き角を120度（V字型）に開くことで、137MHz帯の「Vダイポールアンテナ」として動作します。上空通過時に直接雲写真を受信可能です。

#### 2. 市販パーツ（数千円〜）や軽微な工作を追加してできる観測
- **天の川銀河の観測（[21cm中性水素線](00_glossary.md#21cm)・銀河回転曲線）**:
  - 水素線は電波が微弱なため、[LNA（低雑音増幅器）+ BPF（バンドパスフィルタ）](00_glossary.md#lna) が必須となります（例: Nooelec SAWbird+ H1 等）。
  - アンテナは、Nooelec社の21cm専用パッチアンテナ（約8,000円）を購入するか、市販のWi-Fi用グリッドパラボラアンテナ（2.4GHz用を1.4GHz用に改造・流用）を使うのが世界中のアマチュア電波天文学者の定番です。

### Q. ペアガラスの室内窓際でも観測可能か？ 外に置いたほうがいい？

**A.**
**結論として、「屋外（ベランダや窓の外）」への設置が圧倒的に推奨されます。**
SRE・通信インフラ的な観点で言えば、**「予期せぬ電磁シールド（遮蔽）」**と**「室内ノイズフロアの上昇」**という二重の致命的ペナルティが発生するためです。

#### 1. 最大の障害：「Low-Eガラス（金属膜コーティング）」
現代の住宅やマンションで広く採用されているペアガラス（複層ガラス）の多くには、遮熱・断熱性能を高めるために**極薄の金属酸化物膜（銀コーティング等）**が蒸着されています（Low-Eガラス）。
- **物理的影響**:
  - 電波から見ると、ガラス全体が**「金属板（電磁シールド / ファラデーケージ）」**として振る舞います。
  - これにより電波は **20dB〜40dB（強度が1/100〜1/10,000）も激しく減衰・遮断** されます。スマートフォンが室内窓際で電波が弱くなる主因もこれです。
  - ※通常の透明ガラスでも数dBの減衰がありますが、Low-E膜が存在する場合、宇宙からの微弱電波はほぼ受信不能になります。

#### 2. 室内の電磁ノイズ（RFI: Radio Frequency Interference）
- 室内窓際は、PC、ゲーミングマシンの電源ユニット、Wi-Fiルーター、エアコンのインバーターなどから漏洩する高周波スイッチングノイズに満ちています。
- 宇宙からの信号は極めて微弱（低SNR）なため、室内ノイズフロアに完全に埋もれてしまいます。

#### 推奨される運用スタイル
- アンテナをベランダや屋外の手すり・室外機上などに配置し、薄型フラット同軸ケーブルで引き込むか、
- **小型軽量・バッテリー駆動可能な GPD Pocket3 ごと屋外（ベランダ）に設置し、Wi-Fi経由で自律観測させる（KubeEdgeの真骨頂）** 構成が最も高いS/N比を実現できます。

### Q. 付属の伸縮アンテナは「逆T字」のままでいいのか？（NOAA気象衛星受信用セッティング）

**A.**
**「逆T字（水平180度）」から少し曲げて『120度のV字型（＼／）』にしてあげるのが、人工衛星受信の黄金セッティング（Vダイポールアンテナ）です。**

```text
【逆T字：水平180度】              【衛星受信セッティング：120度 V字】
      ────┬────                              ＼       ／
          │                                   ＼ 120°／
          │                                     └─┬─┘
       (スタンド)                                 │
                                              (スタンド)
```

#### なぜ「120度のV字型」にするのか？
1. **インピーダンスのマッチング（50Ω最適化）**:
   - 水平に真っ直ぐ（180度）伸ばしたダイポールのインピーダンスは約73Ωですが、**120度のV字に曲げることで「約50Ω」へと下がり、SDRや同軸ケーブルの規格（50Ω）と完全にインピーダンス整合**します。これにより反射波ロスがなくなり、受信感度が最大化されます。
2. **天頂方向（空の真上）への感度向上**:
   - 水平ダイポールは真上や特定の角度に電波の谷（感度が落ちるヌル点）ができやすいですが、V字にすることで「上空850kmを通過する衛星」に対して最も高い利得を持つビームパターンが得られます。

#### 付属アンテナのセッティング手順
1. **ロッドの長さを「片側 約53cm」にする（超重要）**:
   - 137MHz帯の波長（$\lambda$）は約2.19mです。
   - ダイポールの片側エレメント長は「1/4波長（$\lambda / 4$）」に合わせる必要があるため、メジャーで測って**片側約53.4cm（約53cm）** に縮めて固定します（伸ばし切ると長すぎます）。
2. **角度を「120度」に開く**:
   - 黒い給電マウントのネジを少し緩め、ロッド同士の挟み角が正三角形の2辺に近い「約120度（水平から上へ30度ずつ持ち上げる）」になるよう調整します。
3. **設置の方角（南北に向ける）**:
   - NOAA衛星は極軌道（北極から南極、または南極から北極）を秒速7.5kmで縦に飛行します。
   - V字の開いている正面（平らな面）を**「南」または「北」**に向けて設置すると、接近から通過、遠ざかるまでの全軌道を安定して追跡できます。

### Q. マグネットベース付きの垂直ホイップアンテナで衛星受信はできるか？ 設置の注意点は？

**A.**
**十分に使えます！特に角度の良い通過（高仰角パス）であればNOAA気象衛星の信号も受信可能です。ただし、設置時に「金属板（グラウンドプレーン）」に載せることが絶対条件となります。**

```text
【マグネットベース付きホイップアンテナ】
       │  (垂直エレメント / モノポール)
       ⌇  (ローディングコイル)
       │
     ┌─┴─┐ (マグネット台座)
  ═══════════════ (金属板 / お菓子の缶のフタ / 室外機天板)
```

#### 1. アンテナの特徴と衛星受信での挙動
- **途中のコイル（ローディングコイル）**:
  - アンテナの物理長を短縮しつつ、VHF（144MHz帯）やUHF（430MHz帯）に共振させるためのものです。
- **真上（天頂）が死角になる特性（ヌル点）**:
  - 垂直モノポールアンテナは「水平方向」の電波に強く、**「真上方向」の感度がゼロ（ヌル点）**になります。
  - そのため、衛星が地平線から昇ってきた時はよく受かりますが、真上を通過する瞬間に一時的に信号強度が落ちる挙動を示します。

#### 2. 【超重要】金属板（グラウンドプレーン）が必須な理由
- アンテナは本来「プラス側とマイナス側（アース）」の2極で電波を捕らえます。
- このようなモノポールアンテナは「プラス側の1本」しか存在せず、**台座をくっつけた「金属板」をアンテナのマイナス側（仮想的な地面・グラウンドプレーン）として利用する構造**になっています。
- **推奨される設置方法**:
  - そのまま机や木の上に置くのではなく、**スチール缶のフタ（お菓子の缶など）、金属製トレー、ベランダの手すり、エアコン室外機の天板** などにマグネットでカチッと吸着させてください。
  - 金属板に載せるだけで、インピーダンス整合が取れて**受信感度が劇的に向上（数倍〜数十倍）**します。

### Q. アンテナケーブルをベランダのドアや窓サッシで挟んで室内に引き込んでも大丈夫？

**A.**
**サッシの「柔らかいゴムパッキン部分」に軽く挟む程度なら大丈夫ですが、金属枠で強く圧迫してペチャンコに潰すのは厳禁です。**

同軸ケーブルは内部が同心円状の精密な二重構造（シールドと芯線）になっています：

```text
【同軸ケーブルの内部断面】
   ┌───────── 外側被覆（PVC等）
  ┌┴───────┐
  │ ░░░░░░ │ 外部導体（金属メッシュ網組 / シールド・グラウンド）
  │ ┌─────┐│
  │ │  █  ││ 絶縁体（ポリエチレン / テフロン）
  │ └─────┘│
  │   芯線  │ 内部導体（高周波信号が通る中心の銅線）
  └────────┘
```

#### 強く挟み込みすぎた場合に生じる3大リスク
1. **内部ショート（短絡）による感度ゼロ化**:
   - 強くプレスされると絶縁体が潰れ、中心の「芯線」と外側の「シールド（網組）」が接触します。信号がグラウンドに逃げるため、受信強度がゼロになります。
2. **インピーダンスの不連続（急激なミスマッチ）**:
   - 芯線とシールドの距離が歪むと、特性インピーダンス（50Ω）が狂います。電波がその潰れた箇所で反射して跳ね返り（反射波ロス）、SDRチューナーまで届かなくなります。
3. **芯線の金属疲労・断線**:
   - 日常的にドアを開閉する場所で挟むと、中の細い銅線が折れて断線します。

#### 推奨される引き込み対策
- **日常の簡易観測**: サッシ上部や側面のゴムパッキンの柔らかい隙間にそっと通し、ドアをロック（鍵締め）まで強く締め込まずにクッションを保つ。
- **本格的な常設観測**: アマチュア無線用の**「窓サッシ用すきまフラットケーブル（通称: 忍者ケーブル）」**を使用するか、エアコンの配管ダクト穴を通して引き込む。

## 3. アプリケーション・システム応用

### Q. 電波観測やエッジ基盤の先に作れる「宇宙向けアプリ」にはどんなアイデアがあるか？

**A.**
GPD Pocket3（エッジDSP）＋ ゲーミングPC（WSL2/Kubernetes）＋ RTL-SDR v4 という構成の強みを活かした、実践的かつユニークな4つのアプリケーション構想です。

#### 1. 自作3D天の川銀河マップ「Galaxy Cartographer」
- **概要**: 自宅ベランダで観測した21cm線のドップラーシフトから星間水素ガスの速度と距離を逆算し、Webブラウザ（Three.js / WebGL）上で天の川銀河の3D構造マップをプロット・探索するアプリ。
- **特徴**:
  - 観測するごとに未探査領域の「霧」が晴れていくマップ解放体験。
  - 銀河回転曲線のグラフを同時に描画し、ダークマターの存在をリアルデータで証明できる。

#### 2. 自宅宇宙天気＆流星アラートコックピット「Space Weather Sentry」
- **概要**: エッジノードが太陽電波バーストや流星前方散乱エコーの急峻なスパイクをリアルタイム検知し、外部宇宙天気API（NOAA GOES衛星やNICT）と突合してアラートを発報する監視コックピット。
- **特徴**:
  - SREのインフラ監視ダッシュボードのように「宇宙のヘルスチェック」を常時可視化。
  - 巨大フレア発生時や流星群極大時に Discord/Slack 通知を飛ばす。

#### 3. ポータブル自律型 地上局アプリ「Personal Ground Station Web」
- **概要**: 人工衛星の軌道要素（TLE）から自宅上空の通過（Pass）時刻を自動計算し、エッジノードが自動で周波数を切り替えて受信・デコードするポータブル地上局アプリ。
- **特徴**:
  - NOAA気象衛星からのリアルタイム日本上空雲写真や、CubeSatのテレメトリが自動でアルバムのように蓄積される。
  - GPD Pocket3 の可搬性を活かし、野外・キャンプ・山頂での即席地上局運用が可能。

#### 4. タイムマシン電波アーカイブ「Cosmic Event Logger」
- **概要**: 24時間365日エッジで蓄積したスペクトルデータ（DuckDB/Parquet）を、WebUI上のタイムバーで任意の過去日時にシームレスにリプレイ・クエリできる時系列基盤。
- **特徴**:
  - 過去の流星群やフレア発生の瞬間をピンポイントで動画（WebP/MP4）やFITS形式にエクスポート。
  - 分散ストレージ・データエンジニアリングとしての完成度が高い。

### Q. 人工衛星の電波データは暗号化されていないのか？ 個人でデコードできるものなのか？

**A.**
**一切暗号化されていません。オープンソースのツールを用いて個人で完全にデコード（画像化・データ化）可能です。**

誰でも自由に受信・復号できる背景には、国際法および電波法上の明確な理由があります：

#### 1. 暗号化されていない理由
- **国際公共財としての気象衛星**:
  - アメリカ海洋大気庁（NOAA）や欧州・ロシアの気象衛星は、世界気象機関（WMO）や国連の枠組みに基づき、世界中の船舶や市民が気象災害から身を守るための「国際人道・公共財」として電波を常時ブロードキャストしています。そのため、暗号化は禁止されており仕様も全公開されています。
- **アマチュア無線帯の法規制（ISS / CubeSat）**:
  - 国際宇宙ステーション（ISS）や大学等の超小型衛星（CubeSat）が利用する144MHz/430MHz帯はアマチュア無線業務として割り当てられています。国際電気通信連合憲章（ITU憲章）および電波法により、**アマチュア無線における通信の秘匿・暗号化は原則違法**と規定されているため、すべての信号・テレメトリは平文・オープン規格です。

#### 2. デコードの仕組みと代表的ツール
受信した電波の音声（WAV）や[IQデータ](00_glossary.md#iq)をオープンソースのデコーダに通すだけで、容易に画像へ復元できます。

- **NOAA 15 / 18 / 19 衛星（137MHz帯）**:
  - 方式: **APT (Automatic Picture Transmission)**。いわば「宇宙からの電波FAX」。地表の走査線をAM変調の可聴音トーンに変えてFM送信。
  - デコーダ: Rust製の高速デコーダ **`noaa-apt`** など。コマンドラインでWAVを入力すると即座に日本列島や雲の白黒・赤外線画像（PNG）を出力。
- **ロシア Meteor-M 衛星（137MHz帯）**:
  - 方式: **LRPT (Low Rate Picture Transmission)**。QPSK変調によるデジタル伝送。
  - デコーダ: **`SatDump`** など。解像度 1km/pixel の極めて高精細なフルカラー地球写真に復号可能。
- **ISS（国際宇宙ステーション / 145.80MHz）**:
  - 方式: **SSTV（Slow Scan TV）**。宇宙飛行士イベント等で記念写真が定期的に送信される。`QSSTV` 等でリアルタイム画像化が可能。

## 4. エッジインフラ・ネットワーク＆デバイス運用（WSL2 / Linux）

### Q. GPD Pocket3（WSL2）にLAN内の別PCから直接SSH接続するには？

**A.**
**Windows 11 の WSL2 であれば、「Mirrored（ミラー）モード」を使用するのが最もシンプルで確実です。**

従来のNATモードではホストのポートフォワーディング（`netsh`）が必要でしたが、Mirroredモードを使用するとWSL2がホストWindowsのLAN IPアドレスを直接共有するため、ポートフォワーディングが一切不要になります。

#### 設定手順
1. **WSL2内で openssh-server を起動**:
   ```bash
   sudo apt update && sudo apt install -y openssh-server
   sudo service ssh start
   ```
2. **Windows側で `.wslconfig` を設定**:
   GPD Pocket3 の `C:\Users\<ユーザー名>\.wslconfig` を作成・編集：
   ```ini
   [wsl2]
   networkingMode=mirrored
   firewall=true
   ```
   PowerShell で `wsl --shutdown` を実行して再起動。
3. **Windows Defender ファイアウォールでポート22を許可（管理者PowerShell）**:
   ```powershell
   New-NetFirewallRule -Name "WSL-SSH" -DisplayName "WSL-SSH-Inbound" -Direction Inbound -LocalPort 22 -Protocol TCP -Action Allow
   ```
4. **接続**:
   別マシンから `ssh <WSLユーザー名>@<GPD Pocket3のLAN_IP>` で直接ログイン可能。

### Q. Windowsホストに接続したRTL-SDRドングルをWSL2へパススルーするには？

**A.**
**Microsoft公式推奨の `usbipd-win` を使用して、USB/IP経由でWSL2にデバイスをアタッチします。**

#### 手順
1. **Windows側で `usbipd-win` をインストール（PowerShell）**:
   ```powershell
   winget install dorssel.usbipd-win
   ```
   （インストール後、PowerShellを再起動）
2. **デバイスの特定とバインド**:
   ```powershell
   usbipd list
   # RTL-SDR（ID: 0bda:2838 など）の BUSID（例: 1-6）を確認
   usbipd bind --busid 1-6
   ```
3. **WSL2へアタッチ**:
   ```powershell
   # --auto-attach を付けると抜き差しや再起動時も自動再接続される
   usbipd attach --wsl --auto-attach --busid 1-6
   ```
4. **WSL2内での認識確認**:
   WSL2ターミナルで `lsusb` を実行し、`Realtek Semiconductor Corp. RTL2838 DVB-T` が表示されれば成功。

### Q. rtl_test -t で「No E4000 tuner found, aborting.」と出るが故障か？ アンテナが電波を拾えているか確認する方法は？

**A.**
**全くの正常動作です。故障ではありません。**

#### 1. 出力メッセージの解説
- `Found Rafael Micro R828D tuner`: RTL-SDR Blog V4 の中核チューナーが正常認識されています。
- `Sampling at 2048000 S/s`: 毎秒204.8万サンプルのIQデータキャプチャが成功しています。
- `No E4000 tuner found, aborting.`: `-t` オプションは旧世代の「E4000」チューナー用の特定ベンチマークを試みるため、E4000ではないV4（R828D）ではこのテストをスキップして終了します。エラーではなく正常終了のログです。

#### 2. アンテナが電波を拾えているか（導通・受信）の確認手順
身近に強力に放射されているFMラジオ放送（80MHz〜100MHz）を `rtl_power` でスキャンし、各周波数の信号強度（パワースペクトル）を測定します：

```bash
# 80MHz〜100MHz を 100kHz 刻みで 10秒間スキャン
rtl_power -f 80M:100M:100k -i 5 -e 10s fm_scan.csv
```

- **正常に受信できている場合**:
  出力されたCSVのデータ列で、放送局の周波数（80.0MHz TOKYO FM、81.3MHz J-WAVE、90.5MHz TBSラジオ等）の数値（dB）が周囲のノイズフロアより 10〜30dB 程度突出して高くなります。
- **アンテナが断線・ショートしている場合**:
  全周波数で平坦な雑音レベルのまま変化が見られません。

### Q. rtl_power 等で「[R82XX] PLL not locked!」が大量に出力される原因と対処法は？（RTL-SDR Blog V4必須設定）

**A.**
**Ubuntu/Debian標準の `apt install rtl-sdr` で入るドライバが旧型チップ（R820T）用であり、V4に搭載された最新チューナーチップ（Rafael Micro R828D）に対応していないためです。**

#### 1. 発生する理由
周波数を合わせるための位相同期回路（PLL: Phase Locked Loop）の制御レジスタの仕様が旧型とV4で異なるため、標準ドライバでは「指定した周波数にロックできない」というエラー（`PLL not locked!`）が連続して発生します。

#### 2. 対処手順（公式V4対応ドライバのビルド＆インストール）
RTL-SDR Blog 公式がメンテナンスしているパッチ適用済みドライバをソースからビルドして適用します：

```bash
# 1. ビルド必須パッケージのインストール
sudo apt update && sudo apt install -y git cmake build-essential libusb-1.0-0-dev

# 2. 公式リポジトリのクローンとビルド
cd ~
git clone https://github.com/rtlsdrblog/rtl-sdr-blog.git
cd rtl-sdr-blog
mkdir build && cd build
cmake ../ -DINSTALL_UDEV_RULES=ON
make -j$(nproc)
sudo make install
sudo ldconfig

# 3. DVB-T（テレビ用）標準カーネルモジュールのブラックリスト化
echo 'blacklist dvb_usb_rtl28xxu' | sudo tee --append /etc/modprobe.d/blacklist-dvb_usb_rtl28xxu.conf
```

ビルド・インストール完了後、ライブラリキャッシュ（`ldconfig`）が更新され、すべてのSDRツールがV4のR828Dチューナーを正常に制御できるようになります。

### Q. エッジで受信したFMラジオをLAN経由でリアルタイム再生（SSHストリーミング）するには？

**A.**
**エッジ側（GPD Pocket3）で `rtl_fm` を使って電波を復調し、その標準出力をSSH経由でクライアント（ゲーミングPC）にパイプで流し、`ffplay` で再生します。**

#### 1. 前提条件：公開鍵認証（パスワードなしSSH）の設定
パイプライン（`ssh ... | ffplay ...`）を使用する場合、標準入力（TTY）がパイプに占有されるため、パスワード入力プロンプトが機能せず認証エラー（`Permission denied`）になります。事前にSSH公開鍵を登録しておく必要があります：

```bash
# クライアント側（ゲーミングPC）で実行
ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
ssh-copy-id <エッジユーザー名>@<エッジIP>
```

#### 2. ストリーミング再生コマンド（FFmpeg 8.0+ 対応）
クライアント側（ゲーミングPC）のターミナルで実行：

```bash
# J-WAVE（81.3MHz）を受信・リアルタイム再生
ssh <エッジユーザー名>@<エッジIP> "rtl_fm -M wfm -f 81.3M -s 200k -r 48k" | ffplay -nodisp -f s16le -ar 48000 -ch_layout mono -
```

- **オプション解説**:
  - `-M wfm`: ワイドFM（FMラジオ放送）の復調モード。
  - `-f 81.3M`: 受信周波数（80.0M: TOKYO FM、90.5M: TBSラジオ等）。
  - `-s 200k`: SDRのサンプリングレート（帯域幅 200kHz）。
  - `-r 48k`: 復調後のオーディオサンプリングレート（48kHz）。
  - `-ch_layout mono`: FFmpeg 8.0以降におけるモノラルチャンネル指定オプション（旧バージョンの場合は `-channels 1`）。

### Q. NOAA気象衛星（15, 18, 19）の周回周期・通過タイミングと電波周波数は？

**A.**
**NOAA気象衛星は高度約850kmの太陽同期極軌道（Sun-synchronous orbit）を約102分で地球1周しており、日本上空を2〜4時間おきに通過します。**

#### 1. 運用中のNOAA-APT気象衛星一覧

| 衛星名 | NORAD ID | 送信周波数 | 方式 | 特徴 |
| :--- | :--- | :--- | :--- | :--- |
| **NOAA 15** | 25338 | **137.620 MHz** | アナログ APT | 1998年打上げ。老朽化により送信機に乱れが出ることがあるが現役。 |
| **NOAA 18** | 28654 | **137.9125 MHz** | アナログ APT | 2005年打上げ。送信電波が強く極めて安定して美しい雲画像が受信可能。 |
| **NOAA 19** | 33591 | **137.100 MHz** | アナログ APT | 2009年打上げ。NOAAシリーズ最後のAPT搭載機。最も安定稼働中。 |

#### 2. 通過サイクルの特徴
- **1日約14周**: 地球の自転に伴って経度が少しずつ移動するため、日本上空の見通し範囲（仰角15°〜20°以上）に入るパスは各衛星ごとに **昼間に2〜3回、夜間に2〜3回** 巡ってきます。
- **ゴールデンタイム（昼間パス）**: 11:00〜14:00頃の昼間パスは太陽光が当たるため、可視光カメラ（チャンネル2）による日本列島や台風・雲の輪郭が最も美しくデコードできます。夜間パスは赤外線カメラ画像になります。

### Q. SGP4とTLEから観測点基準の衛星仰角（Elevation）を計算するアルゴリズムとは？

**A.**
**2行軌道要素（TLE: Two-Line Element）から SGP4 モデルで衛星の地球中心慣性座標（ECI）を推算し、グリニッジ恒星時（GMST）で自転させた後、観測点（WGS84座標）基準の水平座標系（ENU: East-North-Up）へ回転変換して仰角を求めます。**

```text
[ TLE (軌道要素) ] 
       │ (SGP4 軌道伝搬モデル)
       ▼
[ 衛星 ECI 座標 (TEME) ] ──► (GMST 恒星時回転) ──► [ 衛星 ECEF 座標 (地心直交) ]
                                                            │
                                  [ 観測地点 ECEF 座標 ] ◄──┘ (相対ベクトル ρ = Sat - Obs)
                                            │
                                            ▼ (観測点の緯度・経度で回転)
                                  [ 水平座標系 (ENU: East, North, Up) ]
                                            │
                                            ├─► Elevation (仰角) = arcsin(Up / Range)
                                            └─► Azimuth   (方位角) = atan2(East, North)
```

1. **AOS（Acquisition of Signal）**: 仰角が閾値（例: 20°）を超えた時刻。
2. **Max Elevation（最大仰角）**: パス中の最高仰角。この角度が高いほどアンテナ利得が高く、障害物（ビル・山）の影響を受けずに鮮明な画像が得られます。
3. **LOS（Loss of Signal）**: 衛星が地平線・閾値下に没した時刻。

### Q. RustデーモンからVOICEVOX（ずんだもん）を呼び出す仕組みとフォールバック設計とは？

**A.**
**VOICEVOX Engine が提供するローカル REST API（ポート50021）に対し、HTTP POST でクエリ生成と音声波形合成を要求し、取得した WAV をバックグラウンド再生します。**

#### 1. API呼び出しの流れ
1. `POST http://localhost:50021/audio_query?text={発話テキスト}&speaker=3`
   - テキストの音素・アクセント情報を含むクエリ JSON を取得。
2. `POST http://localhost:50021/synthesis?speaker=3`
   - クエリ JSON をボディに入れて送信し、WAV 音声バイナリを取得。
3. 一時ファイルに保存し、`aplay -q`（ALSA）または `ffplay -nodisp -autoexit`（FFmpeg）で再生。

#### 2. SRE視点でのフォールバック設計（重要）
常駐デーモンにおいて、通知サービス（VOICEVOX）の停止が主業務（電波観測・SDR録音）を巻き添えにして異常終了（panic）してはなりません：
- **タイムアウト設定**: HTTP クライアントに短いタイムアウト（3秒）を設定。
- **安全なエラー処理**: `ConnectionRefused` などの接続失敗時は `warn!` ログを出力してスキップし、SDR録音やデコード処理は100%確実に継続します。

### Q. Windows + WSL2 + Docker で動かす場合、Windows のスピーカーから音は鳴らせるのか？

**A.**
**鳴らせます。しかも Docker コンテナにオーディオデバイス（`/dev/snd` 等）をパススルーする必要は一切ありません。**

#### 1. 責任分担とデータフロー

```text
[ Docker コンテナ (voicevox_engine) ]
  │  ▲ ※コンテナは単なる「HTTP計算サーバー (REST API)」
  │  │   テキストを受け取り、WAVデータ（バイナリ）を返すだけ。
  │  │   スピーカーの知識は一切持っていません。
  │  │
  │  │ (HTTP POST :50021)
  ▼  │
[ WSL2 (Rust: noaa-station) ]
  │  └─► HTTPでWAVデータを受信し、一時ファイルに保存
  │  └─► WSL2 内の `ffplay` または `aplay` で再生コマンドを実行
  ▼
[ WSLg (仮想 PulseAudio ソケット) ]
  │  └─► Windows 11 の WSL2 に標準搭載されたオーディオブリッジ
  ▼
[ Windows 11 ホスト (オーディオドライバ) ]
  │
  ▼
🔊 Windows のスピーカー / ヘッドホンからずんだもんの声が鳴る！
```

#### 2. なぜこれで動くのか？
1. **Docker コンテナはスピーカーを必要としない**:
   - コンテナはポート `50021` で JSON と WAV を送受信する Web サーバーとして完結しています。
2. **WSL2 は WSLg でホスト音声と直結している**:
   - Windows 11 の WSL2 には **WSLg（WSL GUI/Audio）** が標準搭載されており、WSL2 内部のオーディオ出力は自動的にホスト Windows のスピーカーへルーティングされます。
   - そのため、WSL2 上の Rust プログラムが `ffplay` や `aplay` をキックするだけで、自然に Windows のスピーカーから音声が再生されます。

### Q. WSL2環境で aplay を実行すると「cannot find card '0'」エラーになる原因と対策は？

**A.**
**WSL2には物理的なALSAサウンドカード（`/dev/snd/*`）が存在しないため、ALSA直接出力の `aplay` は失敗します。PulseAudio対応の `ffplay` を最優先にし、Windows側の `powershell.exe` へのフォールバックを備えるのがベストプラクティスです。**

#### 1. ALSAエラー（cannot find card '0'）の技術的背景
- `aplay` は Linux の古典的なオーディオサブシステムである **ALSA (Advanced Linux Sound Architecture)** を直接叩くコマンドです。
- ALSA はカーネルレベルのサウンドカード番号（Card 0, Device 0）を探しに行きますが、WSL2は軽量仮想マシンのため仮想ALSAデバイスノードが存在しない、または不完全な場合があります。
- 一方、Windows 11 の WSLg はオーディオ転送プロトコルとして **PulseAudio / PipeWire ソケット（`/mnt/wslg/PulseServer`）** を提供しています。

#### 2. 解決策：多段フォールバック設計（Rust実装パターン）
SRE・インフラ視点では、実行環境（GPD Pocket3の実機Linux、WSL2、Docker等）によって利用可能なオーディオスタックが異なることを想定し、以下のような多段フォールバック（Graceful Degradation）を実装します：

```text
[ 音声WAVファイル ]
       │
       ▼ 試行 1: `ffplay` (最優先)
  ┌────┴───────────────────────────────────────┐
  │ WSLg (PulseAudio) に完全対応。             │──► 成功なら即リターン
  │ `-nodisp -autoexit -loglevel quiet` で再生 │
  └────┬───────────────────────────────────────┘
       ▼ 試行 2: `paplay`
  ┌────┴───────────────────────────────────────┐
  │ PulseAudio クライアント標準ツール          │──► 成功なら即リターン
  └────┬───────────────────────────────────────┘
       ▼ 試行 3: `aplay`
  ┌────┴───────────────────────────────────────┐
  │ 実機 Linux (GPD Pocket3/Ubuntu) の ALSA 出力 │──► 成功なら即リターン
  └────┬───────────────────────────────────────┘
       ▼ 試行 4: `powershell.exe` (WSL2の究極フォールバック)
  ┌────────────────────────────────────────────┐
  │ `wslpath -w` でWindowsパスに変換し、       │──► WindowsホストのSoundPlayer
  │ PowerShellの [System.Media.SoundPlayer] を │    で直接再生（100%鳴る）
  │ WSL2から透過的に呼び出し                   │
  └────────────────────────────────────────────┘
```

この設計により、GPD Pocket3実機のUbuntuデスクトップ環境でも、WSL2開発環境でも、コードを1行も変えずに確実にWindows/Linuxのスピーカーからずんだもんの声を鳴らすことができます。

### Q. GPD Pocket3（エッジ）に受信機がある場合、noaa-station はどのようなシステム構成・分担になるか？

**A.**
**noaa-station は「完全エッジ自律型（GPD単体完結）」と「分散エッジ-クラウド型（GPDで受信、ゲーミングPCで発話・分析）」の2通りのデプロイパターンをサポートしています。**

#### 1. パターン A: 【完全エッジ自律型】GPD Pocket3 単体で24時間自律稼働（推奨）
ゲーミングPCの電源が完全にOFF（または外出・ゲーム中）でも、GPD Pocket3 単体で衛星の追跡・録音・デコード・音声通知を全自動で行う構成です。

```text
═══════════════════════════════════════════════════════════════════════════════
【エッジ観測ノード：GPD Pocket3 (ベランダ / 窓際)】※ゲーミングPCの電源OFFでOK！
═══════════════════════════════════════════════════════════════════════════════
  [ 📡 アンテナ (120° V字ダイポール) ]
         │ (137MHz帯)
         ▼
  [ 🔌 RTL-SDR v4 (USB接続) ]
         │
         ▼
  [ 🦀 noaa-station デーモン (Rust) ] ◄── CelesTrakからTLE自動更新
         │
         ├─► [ rtl_fm ] ──► 衛星通過中、自動でWAV録音 (137.9125MHz等)
         │                     │
         ├─► [ noaa-apt ] ◄────┘ 通過終了後、自動でPNG衛星雲画像に復元！
         │                     │
         │                     ▼
         │               [ 💾 ./data/noaa/ に雲画像を永続保存 ]
         │
         ▼ (HTTP POST :50021)
  [ 🐳 Docker: voicevox_engine (GPD上) ]
         │
         ▼
  🔊 GPD Pocket3 の内蔵スピーカー
     「まもなくNOAA 18が来るのだ！最大仰角52度、受信を開始するのだ！」
```

#### 2. パターン B: 【分散エッジ-クラウド型】GPDで受信・デコード、自室のゲーミングPCで発話
「ベランダのGPDは静かに稼働させ、自室のゲーミングPCのスピーカーからずんだもんに通知させたい」という場合の構成です。

- `apps/noaa-station/config.toml` の VOICEVOX URL をゲーミングPCのIPに向けるだけで実現できます：
  ```toml
  [voicevox]
  url = "http://192.168.x.x:50021" # ゲーミングPCのLAN IP
  speaker_id = 3
  ```
- 生成された画像（PNG）は GPD Pocket3 ローカルに保存されるほか、SSH / MinIO / Kubernetes 共有ボリュームを通じてゲーミングPCから直接閲覧・分析できます。

### Q. SSH経由でエッジノード（GPD Pocket3）の観測デーモンを運用する際、tmux は必要か？

**A.**
**極めて推奨されます。SSH切断時の SIGHUP シグナルによるプロセスの道連れ死を防ぎ、いつでも遠隔からリアルタイムログに再アタッチできるためです。**

#### 1. SIGHUP（ハングアップシグナル）問題
- 通常の SSH 接続でフォアグラウンド実行（`cargo run ... daemon`）していると、Wi-Fi の瞬断や操作端末（ゲーミングPC）のスリープ・SSH切断時に、Linux カーネルの擬似端末（PTY）からセッショングループへ `SIGHUP` がブロードキャストされます。
- これにより、観測デーモンが道連れで異常終了してしまいます。

#### 2. tmux による解決と運用メリット
- **仮想端末の分離**: tmux サーバがバックグラウンドで疑似端末を保持し続けるため、SSH セッションを切断（Detach）してもプロセスは一切影響を受けず動き続けます。
- **いつでも再アタッチ可能**: 自室から `ssh gpd` して `tmux a -t noaa` を叩くだけで、現在の待機状況・受信ログ・衛星仰角の進行画面に瞬時に復帰できます。
- **systemd との使い分け**:
  - **tmux**: 開発・検証・初期実機テストフェーズに最適（対話的な再起動やログ目視が容易）。
  - **systemd**: 完全な長期常設運用フェーズに最適（OS再起動時の自動起動、journald 統合、OOMKiller からの自動再起動）。
