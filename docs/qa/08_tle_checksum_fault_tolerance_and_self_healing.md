# TLEチェックサム検証メカニズムと地上局スケジューラの耐障害性・自己治癒アーキテクチャ

## 1. 概要とインシデントの背景

地上局デーモン（`ground-station.service`）において、毎分以下のエラーがログに出力され、追尾・受信・Discord通知処理が完全に停止（ハング状態）するインシデントが発生しました。

```text
[ERROR ground_station::scheduler] パス計算エラー: TLEのパースに失敗しました: Error { message: "bad checksum" }
```

本ドキュメントでは、NORAD TLE（Two-Line Element）の規格仕様、チェックサムの厳密な数学的メカニズム、SGP4 軌道伝搬器のバリデーション挙動、そして単一衛星の破損データが地上局全体を道連れにしないための**耐障害性（Fault-tolerance）と自己治癒（Self-healing）システムアーキテクチャ**について無線工学・軌道力学・分散システムの観点から解説します。

---

## 2. TLE（Two-Line Element）の規格とチェックサムの数学

### 2.1 TLE の基本構造
TLE は、地球周回軌道上の人工衛星の軌道要素（ケプラーの法則を拡張した平均軌道要素）を 69 桁・2 行の固定長テキストで表現する世界標準フォーマットです。

```text
1 40903U 15049J   26248.12345678  .00002145  00000-0  11452-3 0  9991
2 40903  97.2890 285.1234 0012345 120.4567 240.1234 15.28901234567894
```

### 2.2 modulo 10 チェックサムの数式

各行（Line 1 および Line 2）の 69 文字目は、1〜68 文字目までのデータを検証するためのチェックサム文字です。

$$CS = \left( \sum_{i=1}^{68} w(c_i) ight) mod 10$$

#### 記号一覧

| 記号 | 意味・定義 | 単位 / 取りうる値 |
| :--- | :--- | :--- |
| $CS$ | 行末（69文字目）に記録されるべきチェックサム数字 | $0, 1, 2, \dots, 9$ |
| $c_i$ | TLE 行の $i$ 番目の文字（1-indexed） | ASCII 文字 |
| $w(c)$ | 文字 $c$ に対する重み付け変換関数 | 整数値 |
| $mod$ | 剰余演算子（10 で割った余り） | - |

#### 重み付け関数 $w(c)$ の定義

$$w(c) = \begin{cases} n & (c \text{ が数字 } '0' \sim '9' \text{ のとき、その数値 } n) \\ 1 & (c = '-') \\ 0 & (c \text{ が文字、空白、'+'、'.' などの場合}) \end{cases}$$

#### 日本語での読み解き
行の先頭（1文字目）から68文字目までの文字列を1文字ずつ走査し、**「数字はその数値をそのまま加算し、マイナス記号（`-`）は 1 として加算し、それ以外のアルファベットやスペース、プラス記号、小数点などはすべて 0 として無視」**します。その総和を 10 で割った余り（一の位）が、末尾の 69 文字目に記載された数字と完全に一致しなければなりません。

#### 不整合の実例と展開ステップ（XW-2A の事例）
障害発生時の `default_tles.txt` に記載されていた XW-2A (Line 1):
```text
1 40903U 15049J   26248.12345678  .00002145  00000-0  11452-3 0  9990
```
- **Line 1 の走査**:
  - 数字: $1 + 4 + 0 + 9 + 0 + 3 + 1 + 5 + 0 + 4 + 9 + 2 + 6 + 2 + 4 + 8 + 1 + 2 + 3 + 4 + 5 + 6 + 7 + 8 + 2 + 1 + 4 + 5 + 0 + 0 + 0 + 0 + 0 + 1 + 1 + 4 + 5 + 2 + 3 + 0 + 9 + 9 + 9 = 140$
  - 符号: `00000-0` の `-` が 1 個 ($+1$), `11452-3` の `-` が 1 個 ($+1$) $\\implies$ 合計 $140 + 1 + 1 = 141$
  - チェックサム: $141 \bmod 10 = 1$
  - **不整合**: 記載されていた末尾文字は `0` であったため、$1 \neq 0$ となり SGP4 パーサーによって `Error { message: "bad checksum" }` が発生しました。正しい末尾文字は `1` です。

## 3. SGP4 軌道伝搬モデルがチェックサムを要求する物理的理由

SGP4（Simplified General Perturbations 4）は、地球の重力ポテンシャルの非対称性（地球帯調和計数 $J_2, J_3, J_4$）や高層大気の抵抗係数（$B^*$ パラメータ）を考慮して未来の衛星位置ベクトル $\mathbf{r}(t)$ および速度ベクトル $\mathbf{v}(t)$ を解く解析モデルです。

もしチェックサムの検証を行わずに 1 桁でも数字が化けた（例: 離心率 $e$ や平均運動 $n$ の桁ズレ）パラメータを SGP4 に入力すると、以下の深刻な計算破綻が生じます：

1. **離心率の幾何学的破綻**: 離心率 $e \ge 1.0$ と解釈され、閉じた楕円軌道ではなく双曲線・放物線軌道（脱出軌道）となり、ケプラー方程式の反復解法（ニュートン・ラフソン法）が発散または NaN を出力。
2. **近地点高度の地下貫通**: 軌道長半径と離心率の積が地球半径 $R_E \approx 6378.137\text{ km}$ を下回り、地球内部を周回する非物理的な解となる。
3. **特異点によるクラッシュ**: 傾斜角や昇交点赤経の計算において逆三角関数（$\arccos, \arcsin$）の引数が $[-1, 1]$ の定義域を超えて数学的例外（パニック）を引き起こす。

したがって、パーサーがチェックサム不整合を即座にエラーとする挙動は、不正な浮動小数点計算や暴走を未然に防ぐための**極めて正当な安全機構**です。

## 4. 地上局アーキテクチャの脆弱性と改修設計

### 4.1 従来の脆弱性（All-or-Nothing による連鎖停止）

```text
[CelesTrak / ミラー API] ──(一部タイムアウト)──► [同梱 default_tles.txt (XW-2A破損)]
                                                              │
                                                              ▼
                                                   [cached_satellites]
                                                              │
   ┌──────────────────────────────────────────────────────────┴─────────────────────────┐
   │                                                                                    │
   ▼                                                                                    ▼
Meteor-M (正常)                                                                  XW-2A (破損)
   │                                                                                    │
   │                                                                                    ▼
   │                                                                       Elements::from_tle FAIL
   │                                                                                    │
   │                                                                                    ▼
   └──────────────────────────► predict_all_passes が ? で即死 ◄────────────────────────┘
                                           │
                                           ▼
                            scheduler メインループがエラー
                                           │
                                           ▼
                      cached_satellites が保持されたまま 60秒 sleep
                                           │
                                           ▼
                     24時間後まで TLE 再取得されず永久ハング (Discord通知停止)
```

### 4.2 改修後の耐障害性（Fault-tolerant）＆ 自己治癒（Self-healing）モデル

多層防御（Defense in Depth）と障害分離（Fault Isolation）により、外部環境や一部のデータ破損に耐える堅牢なシステムへ進化させました。

```text
層 1: データ正常化 (default_tles.txt)
      XW-2A, SO-50 のチェックサムを完全修正

層 2: TLE ロード時事前バリデーション (build_satellite_infos_from_db)
      Elements::from_tle で事前検証。破損 TLE は警告ログを出して即座に除外
      ⇒ 不正データが cached_satellites にそもそも混入しない

層 3: 軌道計算ループの障害分離 (OrbitPredictor::predict_all_passes)
      各衛星の計算を match で受領。1機がエラーでも warn! を出してスキップ
      ⇒ 他の健全な全衛星（Meteor, ISS, CubeSat等）のパス計算を100%完遂

層 4: スケジューラの自己治癒ループ (run_daemon)
      万が一パス計算全体が異常終了した場合は cached_satellites.clear() を実行
      ⇒ 次回ループで即座に最新 TLE の再取得・再構築を試行
```

## 5. 検証と成果

1. **単体テストによる恒久保証**:
   - `test_default_tles_all_valid_sgp4`: 同梱の全衛星 TLE が SGP4 パーサーで 100% 正常にパースできることを保証。
   - `test_predict_all_passes_fault_tolerance`: 不正なダミー衛星がリストに混ざっても、正常な衛星（ISS 等）の通過パスが欠損なく抽出されることを保証。
2. **実機スケジュール計算の確認**:
   - `cargo run --bin ground-station -- schedule` を実行し、全 9 機の衛星（Meteor-M N2-3/4, ISS, FUNcube-1, SO-50, XW-2A, UmKA-1, SONATE-2）の今後 24 時間通過パスが完璧に計算・表示されることを確認しました。
