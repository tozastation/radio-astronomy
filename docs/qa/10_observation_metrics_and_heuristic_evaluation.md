# 衛星通過観測の成否メトリクス管理と「中身が見える」判定基準

本ドキュメントでは、地上局自律観測デーモンにおける各衛星通過（パス）の成否メトリクス管理基盤、ファイル永続化方式（JSON Lines）、および「受信データの中身が見える」ことを成功条件としつつ検知困難な対象を割り切る「あきらめる作戦」の工学的・数理的背景について解説します。

---

## 1. 観測成否メトリクスの設計思想

### 1.1 「生データ保全」と「受信成功」の分離
電波観測システムにおいて、最も陥りやすい落とし穴は「SDRがプロセスとして正常終了し、WAVや生IQファイル（`raw.u8`）がディスクに保存されたこと」をもって「受信成功」と誤認してしまうことです。

電波工学および情報理論の観点から見れば、アンテナが捉えたものが衛星からの真の直達信号なのか、あるいは単なる環境雑音（熱雑音・都市ノイズ・空電）なのかは、**ベースバンド信号から情報（画像・パケット・テキスト）が復号されたかどうか**によってのみ検証可能です。

そのため、本地上局システムでは**「受信データの中身が人間またはシステムに見える形（画像ファイル、テレメトリJSON数値、復号テキスト）で復元できた状態」**のみを「成功（`success`）」と厳密に定義します。

---

## 2. 「検知が難しいものはあきらめる作戦」の工学的合理性

### 2.1 自動検知のトレードオフと偽陽性リスク
あらゆる通信方式に対して100%自動で成否を判定しようとすると、過剰に複雑なヒューリスティックや機械学習モデル（音声区間検出 VAD や音声認識 ASR 等）が必要となり、以下の問題が生じます：

1. **偽陽性（False Positive）**: 空電ノイズやスケルチのバースト音を「交信あり」と誤認する。
2. **計算リソースの圧迫**: エッジノード（GPD Pocket3等）において、本来のSDR録音やFFT処理に遅延やパケットドロップを誘発する。
3. **パイプラインの脆弱性**: 外部ツールや複雑な推定ロジックのクラッシュが観測ループを巻き込む。

### 2.2 3値分類（Success / Failure / Unknown）モデル
そこで本システムでは、**「客観的かつ決定論的に中身が確認できるものは白黒をつけ、判別が曖昧なものはあきらめて保留（`unknown`）とする」**アプローチを採用しました。

| 信号方式・対象 | 成否判定 (`outcome`) | 判定条件（データの中身が見えるか） | 工学的理由・背景 |
| :--- | :--- | :--- | :--- |
| **気象衛星画像**<br>(NOAA APT, Meteor LRPT, SSDV) | **`success`** / **`failure`** | 生成画像（PNG/JPG）が存在し閲覧可能なら `success`。<br>パケット0件・画像未生成なら `failure`。 | スキャン同期またはQPSKシンボル同期が確立して初めて画像ファイルが生成されるため、成否が極めて客観的。 |
| **CubeSat テレメトリ**<br>(FUNcube, UmKA-1, ISS APRS) | **`success`** / **`failure`** | テレメトリJSON項目または復調パケットが1件以上存在すれば `success`。<br>0件なら `failure`。 | CRCチェック（巡回冗長検査）を通過した有効パケットのみがカウントされるため、ノイズによる誤判定がない。 |
| **CW モールス**<br>(XW-2A, CAS-4A) | **`success`** / **`failure`** | モールス復号テキスト（コールサインやテレメトリ文字列）が得られれば `success`。<br>文字抽出0件なら `failure`。 | 単なるビート音の存在ではなく、復号アルゴリズム（適応スケルチとコヒーレント積分）により文字が読めたかを基準とする。 |
| **FM 音声中継**<br>(SO-50 等) | **`unknown`**<br>（あきらめる） | 常に保留（判定対象外）とする。 | 録音されたWAVにアマチュア無線の交信音声が存在したか、単なるFMスケルチのノイズフロアかを自動判別するのは困難なため。 |
| **外部デコーダ未導入**<br>(生データ保全のみ) | **`unknown`**<br>（あきらめる） | 常に保留（判定対象外）とする。 | satdump や multimon-ng が未導入の環境では生データ保全（`RawPreserved`）が行われるが、これは復調未実行であり「中身が見える段階」に達していないため。 |

## 3. 成功率の数理モデル

### 3.1 成功率計算式
保留（`unknown`）を判定母数から除外することにより、判定可能なパスに対する真の成功率（Quality of Reception: QoR）を算出します。

$$R_{\text{success}} = \begin{cases} \dfrac{N_{\text{success}}}{N_{\text{success}} + N_{\text{failure}}} \times 100 & (N_{\text{success}} + N_{\text{failure}} > 0) \\[1em] 0.0 & (N_{\text{success}} + N_{\text{failure}} = 0) \end{cases}$$

### 3.2 数式の構成要素と意味

#### ① 記号一覧
| 記号 | 単位 | 意味・定義 |
| :--- | :--- | :--- |
| $R_{\text{success}}$ | $\%$ | 判定対象パスにおける受信・復調成功率 |
| $N_{\text{success}}$ | 件 | データの中身（画像・パケット・テキスト）が確認できた観測パス総数 |
| $N_{\text{failure}}$ | 件 | 電波微弱（パケット0件・画像未生成）またはデコーダ異常終了の観測パス総数 |
| $N_{\text{unknown}}$ | 件 | 検知困難（FM音声録音）または未復調保全によりあきらめた観測パス総数 |
| $N_{\text{total}}$ | 件 | 全観測パス総数（$N_{\text{total}} = N_{\text{success}} + N_{\text{failure}} + N_{\text{unknown}}$） |

#### ② 日本語での読み解き
「自動検知が不確実な対象（$N_{\text{unknown}}$）を分母から除外し、成否が客観的に確定したパス（$N_{\text{success}} + N_{\text{failure}}$）の中において、実際にデータの中身まで到達できた割合をパーセンテージで評価する」ことを意味します。

#### ③ 展開ステップと直感イメージ
もしあきらめた対象（SO-50等のFM音声録音）を一律に失敗（Failure）に含めてしまうと、システムが正常に動作していても見かけ上の成功率が大きく低下してしまいます。逆に一律に成功（Success）に含めると、実際にはノイズしか録音できていなくても高成功率と誤認してしまいます。
未知の事象を判定母数から分離するこの手法は、SREや分散トレーシングにおける「エラーバジェット計算」や統計的仮説検定の「棄却域の除外」と同じ数理的アプローチです。

## 4. ファイル永続化フォーマット: JSON Lines (`data/metrics/passes.jsonl`)

### 4.1 なぜ JSON Lines なのか
メトリクス管理の第1段階として、リレーショナルデータベースやPrometheusではなく、追記型 JSON Lines（`.jsonl`）を採用しています。

1. **アトミックな追記（Append-only）**: 各パス完了時に1行書き加えるだけであり、ファイル全体の書き換えや破損リスクが極小。
2. **インフラ・SREツールとの親和性**: `jq`、Python（`polars`/`pandas`）、DuckDB による直接クエリが即座に実行可能。
   ```bash
   # 例: DuckDB で JSON Lines を直接 SQL 集計
   duckdb -c "SELECT satellite, count(*), count(CASE WHEN outcome='success' THEN 1 END) FROM 'data/metrics/passes.jsonl' GROUP BY satellite;"
   ```
3. **将来の Prometheus / Grafana エクスポート容易性**: 各行のキーがそのまま Prometheus メトリクスのラベル（`satellite`, `signal_type`, `outcome`）に1対1でマッピング可能。

### 4.2 レコードスキーマ
```json
{
  "timestamp": "2026-09-15T12:02:56.133362964+09:00",
  "satellite": "XW-2A",
  "frequency_hz": 145660000,
  "signal_type": "CubeSat Morse (モールスCW)",
  "max_elevation_deg": 45.0,
  "peak_azimuth_deg": 90.0,
  "status": "AudioRecorded",
  "outcome": "unknown",
  "content_viewable": false,
  "content_summary": "CubeSat XW-2A (145.660MHz) CW モールス復調完了 (音声/画像生成)",
  "session_dir": "./data/noaa/20260915_080935_XW-2A",
  "has_image": true,
  "has_audio": true,
  "has_telemetry_or_text": true,
  "duration_secs": 600
}
```

## 5. CLI コマンドによる確認

地上局 CLI から以下のコマンドで、メトリクス集計サマリーおよび直近の観測履歴をいつでも確認できます。

```bash
cargo run --bin ground-station -- metrics
# 直近 20 件を表示する場合:
cargo run --bin ground-station -- metrics --limit 20
```

### 5.2 毎朝のデイリースケジュール配信（07:00 JST）との自動統合
地上局デーモン（`ground-station daemon`）は、毎朝 07:00 JST に当日の衛星通過予定を Discord へ自動送信する「デイリースケジューラ」を備えています。
本機能により、デイリー配信メッセージ内に**「本日の通過予定一覧 Embed」と「これまでの観測成否メトリクス Embed」が 1 つの通知に美しく連続してパッケージング**され、毎朝起床時に前日までの実績と当日の予定を一目で確認できます。

### 5.3 CLI からの Discord 即時レポート送信
手動でメトリクスレポートを Discord へ送信したい場合は、`--discord` フラグを付与して実行します：

```bash
cargo run --bin ground-station -- metrics --discord
```
